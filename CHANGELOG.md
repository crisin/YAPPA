# Changelog

One line per finished task (definition of done). Newest first.

## Unreleased

- Server setup for machines that already publish apps through a Cloudflare Tunnel (`infra/livekit/tunnel.yml`, guide in the help).
- Admin in the app: invite links with one click, channels, who runs which version, roles, kick, minimum version and the event log.
- First start in three steps: name, microphone check with a live level, how you talk (headset or speakers) — then straight into the lobby.
- Settings have two views: „Einfach“ for everyday use and „Profi“ with the signal chain (every stage with its live level and parameters, CPU cost and added latency), keys, network, updates and diagnosis.
- Easier server setup: `cargo xtask local` starts the whole server stack on the dev PC in one command (`--lan` for other PCs at home), and the home-server guide is one straight path — clone, two lines of `.env`, one command, admin link.
- Push-to-talk and voice settings: „Ich → Audio und Sprechen“ now chooses automatic, hold-a-key or always-on, sets the voice threshold against a live meter, picks the push-to-talk key (also a mouse side button — it works while a game has the focus), the noise suppression, the input of a multi-channel interface and the overall volume. The server box can create channels (`yappa-control channel add`). A checklist for the first evening with the gang: docs/testabend.md.
- The voice chain is live (E1): every microphone now goes through high-pass, DeepFilterNet noise suppression, voice activation, EQ and compressor before it is sent — 10 ms extra latency, about 1.5 ms of work per 10 ms block. Push-to-talk works in the engine; the global key comes with S3. The diagnosis shows the chain's cost.
- Noise suppression measured (S2): DeepFilterNet 3 removes the noise between words completely and costs 0.66 ms per 10 ms block, RNNoise takes ~33 dB off at 0.03 ms; both add 10 ms. DeepFilterNet becomes the default (ADR-008), RNNoise the fallback. New building blocks for the voice chain: noise gate with hold and hysteresis, compressor. Not wired into the app yet (E1).
- Engine groundwork for the voice chain (E0): the microphone path keeps full precision until it is sent, a microphone on the second input of an audio interface can be chosen, a master volume and a limiter stop everyone-laughs-at-once from clipping, and the diagnosis shows how long the send chain takes per block. Measured before and after: about 1 % of the 5 ms budget.
- The app talks to the real server (U5): clicking an invite link opens yAPPA with the link already filled in (also when it is running — no second window), a name, „Beitreten“, and the channel tree is live from the server's presence room. Tester guide rewritten for links.
- Channels in the app (U2): the sidebar shows every channel with the people in it — who is muted, on push-to-talk or away, who speaks — and one click joins; another click switches, the voice box leaves. The first start asks for the invite link and a name; developer invites still work. „Ich → Konto“ shows who you are and logs out. Runs against the mock gang until U5 connects the real server.
- Client core (C1): the app can now log in with an invite link (`yappa://invite/<code>?server=…`), keeps the login in the Windows credential manager / macOS keychain, sits in the presence room and sees who is online and in which channel, joins channels with tokens from the control plane, and remembers channels and config for when the server is away. Settings split into audio (engine) and app settings; old settings files are converted. `YAPPA_PROFILE=<name>` runs a second client on the same PC. The UI is wired to it in U5.
- Control plane (S6): `yappa-control` hands out invite links, channels and LiveKit tokens, keeps the minimum version and a kill switch, and writes an event log from LiveKit's webhooks; the first start prints an admin invite. Runs next to LiveKit in `home.yml` (Caddy publishes it under `/api/`), locally with `cargo xtask control`. The spike confirmed presence over a LiveKit room: a channel switch shows in about a millisecond on one machine, a kick in 10 ms, a crashed client after 20–23 s. Result in docs/spikes/s6-control.md.
- New window layout (U1): module rail on the left (Voice, Ich), the channel with its people in the sidebar, the voice box with mute, deafen and leave always at the bottom left, a search bar with `Strg K` that jumps anywhere, one banner line for problems (reconnecting, server unreachable, version too old), details for a person on the right, `Esc` steps back. Settings, diagnosis (the former debug panel) and help moved into „Ich“; the theme is remembered.
- UI foundation (U0): the second door `api.ts` with a mock control plane and presence room ("Die Gang" fixture, admin actions), mock scenes for browser mode and tests (`cargo xtask dev --ui --scene call|lobby|member|reconnect|offline|update`), the shell state with module registry, banner slot and palette commands, design tokens v1 (widths, type scale, state colours, focus, motion), Bits UI + Lucide installed, accessibility checked with axe in the UI tests. `api-types`: `Me`, `PublicConfig`, `Member`, `InviteCode`, `EventEntry`, `PresenceState` with the presence-room attribute mapping; `Presence` removed before it was ever used.
- Vision and architecture v1 (`docs/01-vision-v1.md`): full review after the UI concept — presence and live data move to a LiveKit presence room (ADR-005), settings split into engine and app schemas with a new `crates/client` for the non-audio client logic (ADR-007), settings become the module „Ich“ instead of an overlay and the UI gets Bits UI + Lucide (ADR-004), updates and remote config come from our own box and the repo goes to GitHub private (ADR-006). Realtime review of the engine (sound base; small prep E0 before the DSP chain), latency budget revisited, mobile sketched only. `TASKS.md` reorganised into the four phase-1 milestones M1–M4.
